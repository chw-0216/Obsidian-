## 三、实际处理链路

```text
SQLite 中读取未完成片段
        ↓
按消息数和预计输出长度分组/切片
        ↓
32 个异步 worker 从队列领取任务
        ↓
Pass A：逐条消息标注
        ↓
Pass B：片段上下文、事件、关系信号
        ↓
Pass C：实体与事件合并
        ↓
独立 SQLite writer 写入结果
        ↓
JSONL checkpoint 追加保存
```

具体机制：

1. `aiohttp` 长连接池保持连接复用，初始 32 workers；每 3 分钟根据错误率和吞吐尝试 32、64、96、128、192、256。
2. 片段按消息数自适应：单消息约 8–12 个一组，2–3 条约 4–6 个一组，中等片段约 2 个一组，长片段按约 12 条消息切片。
3. 每个片段依次经过 Pass A、B、C；A 阶段要求返回消息证据 ID，并做严格校验，避免模型漏标或串标。
4. 429 会退避约 5 秒后重新入队；API 错误或超时约 2 秒后重新入队。
5. 每个完整结果写入 `aggressive_annotations`、消息标注、实体和事件表，同时追加到 `runs\jsonl_checkpoints\checkpoint-*.jsonl`。
6. 进度每 60 秒打印一次，包括完成数、消息标注数、input/output tok/min、workers、队列、成功率、429、超时和磁盘空间。

## 四、当时为什么会很快

旧同步版本大约每分钟 2–3 个片段；异步版本把等待网络响应的时间重叠起来，并把连接、worker、数据库写入和检查点拆开，所以 output tokens/min 显著上升。历史记录中 100/6303 时达到约 119.8K output tokens/min，后来可见最高约 124K。

需要注意：脚本中的“自适应分组”主要用于控制片段大小和切片；当前 worker 实际调用 Pass A 时仍是一次发送一个片段，并不是把整组片段合并成一次 API 请求。每个片段仍要进行三次模型调用，因此 output tokens/min 不能直接换算成片段完成速度。

## 五、结果和断点

运行后检查：

```text
01_主项目_WeChat-MiMo-Analyzer\data\wechat-private-v2.sqlite3
01_主项目_WeChat-MiMo-Analyzer\runs\jsonl_checkpoints\checkpoint-*.jsonl
```

脚本重新运行时，会通过 `aggressive_annotations` 左连接跳过已经完成的片段，因此可以续跑。历史那次被停止时最终为 140/6303，并没有完成全量 6303 个片段。

## 六、复现前检查清单

- 先备份 `data` 文件夹，不删除原始 WeFlow 导出。
- 确认 Token 通过环境变量或 Claude 设置提供，不写入文件。
- 确认 API 地址和模型仍可用；DeepSeek 的 OpenAI 兼容接口不能直接替换这个 Anthropic 请求格式。
- 先用极小范围或测试数据库验证返回结构，再扩大并发。
- 运行中监控 429、超时、磁盘空间和未完成片段数。
- 停止后核对数据库计数与 JSONL 检查点，不要只看 Token/min。
