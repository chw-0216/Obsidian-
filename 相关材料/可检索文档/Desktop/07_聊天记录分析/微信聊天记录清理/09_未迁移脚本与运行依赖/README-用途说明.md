## 目录说明

### scripts/root

27 个一次性脚本：

- `check_*.py`：检查数据库、片段、标注、画像和 Token 统计。
- `find_*.py`、`search_*.py`：筛选重点联系人和搜索联系人名称。
- `layer2_prepare.py`、`layer2_generate*.py`：生成 Layer 2 分析计划和采样任务。
- `layer2_*_execute.py`：调用 MiMo 完成通用、重点、指定联系人和第二批任务。
- `layer2_remaining.py`、`layer2_summary.py`：整理剩余任务和汇总配置。
- `layer2_show_*.py`：查看已有 Layer 2 JSON 结果。

这些脚本多数依赖主项目数据库和相对路径，迁移后作为历史复现材料保存，不能直接在本目录随意运行。

## 关于“147K Token/分钟、52分钟完成”

这条工作流已经在 Claude Code 的本地历史中找到，记录文件是 [Claude 高吞吐运行记录](<C:/Users/wardc/.claude/projects/C--Users-wardc-Desktop/b12c4886-6107-41fc-b545-e2a8b906e380.jsonl:440>)。它不是一份已经完成的全量结果，而是 2026-08-02 运行 `src/async_executor.py` 时的实时进度：

- 100/6303 个片段时，32 workers、100% 成功，约 119,800 output tokens/min，日志估算剩余约 52 分钟；
- 随后最高可见约 124K output tokens/min；这份历史中没有出现精确的 147K 数值，147K 可能是另一张未归档的监控快照或记忆中的峰值；
- 任务后来被停止，最终数据库状态是 140/6303（约 2.2%），所以“52 分钟完成”是当时按短期速率外推的预计值，不是实际完成时间。

还有一条独立的旧同步执行器记录，约 3 个片段/分钟，估算剩余约 3,152 分钟，也就是约 52 小时。这个“52 小时”和高吞吐记录的“52 分钟”曾同时存在，容易被混为一谈。

高吞吐版本之所以明显更快，是因为它在修复响应格式和证据 ID 兼容问题后，使用了异步长连接、32 workers、短片段合批，以及独立 SQLite writer；但每个片段仍需要 Pass A/B/C 三次调用和写库，不能只用 output tokens/min 直接等同于最终片段完成速度。

当时真正提高效率的设计是：

1. `urllib` 同步请求改为 `aiohttp` 长连接池；
2. 单消息片段合并成 8–12 个一批，大片段按窗口切分；
3. 将消息标注、上下文标注、实体事件合并拆成 Pass A/B/C；
4. API worker 与 SQLite writer 分离；
5. 每个结果立即写入 JSONL 检查点，并用输入哈希避免重复调用；
6. 用 Token/min、错误率和 429 动态选择并发。

完整设计见桌面归档中的 `03_规划文档_Claude-Code-MiMo/05-最激进到期冲刺补丁.md`、`07-无上限全量标注理解优先补丁.md`、`08-Claude-Code-MiMo一键完整总流程.md`，实际代码见 `01_主项目_WeChat-MiMo-Analyzer/src/async_executor.py`。

按这次历史运行逐步复现时，使用同目录的 `高吞吐异步标注流程-复现说明.md`。其中特别标出了桌面归档需要修正的数据库、运行目录和 vendor 依赖路径；当前脚本不能直接照抄历史绝对路径运行。
