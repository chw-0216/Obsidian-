# DEEP-REVIEW-SPEC · 深度预判复核规范

## 目标

复核页不是空白标注表，也不是把原始聊天重新交给用户阅读。它必须交付**已经经过充分检索、交叉验证和反证搜索的预填判断档案**；用户只需确认、纠正或推翻高影响判断。

本规范的两个强制改动如下。

## 改动一：深度预填判断档案

每个事件卡片在交给用户前，必须由分析层预填下列内容：

1. 候选事件名称、时间范围、跨联系人参与者和完整证据包。
2. 最强事件解释（发生了什么）、表面目的和模型推测的潜在目的。
3. 最强关系解释：用户与各联系人的关系定位、事件中的实际角色、互惠/权力/资源结构、用户可能的期待、对方可能的期待。
4. 备选解释和反证：主动检索至少一种可替代解释，并列出不支持主结论的证据。
5. 价值和行动假设：成长、合作、情感互惠、资源、风险、边界，以及“若该判断为真，下一步应如何沟通”。
6. 每项结论的证据引用、事实/推测/未知状态和置信度。

模型可进行多轮内部推理，但交付物只能包含可核验的结论、简洁理由、证据、反证和不确定性；不得输出完整思维链，也不得将推测伪装为事实。

稳定的人格、关系或沟通模式，至少需要三个相互独立、已确认事件支持；未满足时只能写为“暂定假设”。

## 改动二：低负担人工确认界面

复核页必须展示预填内容，而非要求用户从空白字段手填。每张卡的主要操作为：

- 确认；
- 部分正确；
- 错误；
- 合并/拆分事件；
- 一句真实背景补充；
- 对关系、期待、价值和建议的关键修正。

用户可查看原始证据、反证和关联联系人，但不应被要求重新阅读整段聊天。所有被用户修改的字段必须保留原模型猜测、用户修正、时间和理由，便于后续重新评估。

## 实施分层

### 无 API 阶段（当前授权）

- 完成事件候选、证据检索、跨联系人召回、反证槽位、预填档案 schema、复核页交互和本地测试。
- 可以基于确定性证据生成“待深度分析”卡片，但不能假装已完成模型级深度推理。
- 生成约 30 个高信号事件候选的无 API 复核包，并明确每张卡的深度分析状态。

### 深度分析阶段（需用户另行确认）

1. 对已确认的高信号事件，收集完整事件包和跨联系人证据。
2. 用多步分析生成主结论、备选解释、反证与沟通建议。
3. 将深度判断预填入复核卡，供用户低负担确认。
4. 记录每个事件包的 token、模型、提示词版本、证据覆盖率和失败情况。

不得直接对 6,303 个片段全量调用深度分析；先给出事件数量、每事件包大小和 token 预测，经用户确认后分批执行。

## 代码与测试要求

- 事件 schema 与复核 schema 应新增对 `deep_hypotheses`、`alternative_hypotheses`、`counter_evidence`、`analysis_status`、`confidence`、`user_verdict` 和 `user_correction` 的可追溯支持。
- `src/v3_event_review.py` 需将预填档案显示在首屏，用户的主要操作是确认/纠偏而非空白输入。
- 任何推断均可回链到 `message_id` / `segment_id` / `candidate_id`。
- 新增无 API 测试：预填字段保存/导出/再导入幂等；模型猜测与用户修正并存；反证槽位存在；不足三事件的稳定结论被标为暂定。

## 安全与边界

- 聊天记录不等于完整现实：面谈、电话、群聊、未导出内容必须视为未知，不能编造。
- 不对联系人做道德评判或操控性建议；沟通建议只服务于清晰、尊重和边界。
- 仅写当前工作区；历史表、原始导出与主项目保持只读。
