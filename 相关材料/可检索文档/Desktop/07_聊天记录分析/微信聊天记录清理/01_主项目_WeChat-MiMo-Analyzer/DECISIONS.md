# DECISIONS.md — 设计决策记录
> 更新时间：2026-08-02

## 为什么先全量标注
- 标注是所有下游产品的基础：记忆、判断、教练、分身全部依赖标注数据
- 未标注的片段无法被检索、分析或引用
- 标注覆盖率直接影响记忆系统的完整性和判断的可靠性
- 用户指令明确：「全量标注完成前至少80% worker用于未覆盖标注」

## 为什么消息级和片段级 Schema 需要拆分
- 单次调用同时输出消息级+片段级+实体+事件+关系 → 输出 token 超 16K 上限
- 60条消息片段的全字段输出约 9734 tokens，加上片段级分析会超限
- 拆分后每 Pass 独立控制 max_tokens，失败时只需重试单个 Pass
- 不同 Pass 可以用不同批次大小（消息级可以批量，片段级逐个）

## 为什么不能只用片段/分钟衡量吞吐
- 片段大小差异巨大：1消息 vs 60消息，处理时间差 10 倍
- Token/min 才是真实资源消耗指标
- 并发优化的目标是最大化 API 利用率，而非最小化等待时间
- 32 workers 的 tok/min 可能高于 128 workers（后者错误率高导致浪费）

## 为什么成功结果按哈希复用
- 相同输入+相同 prompt → 相同输出，不需要重复调用 API
- content_sha256 变化说明片段内容被修改，需要重新标注
- 节省 Token 预算，避免重复工作
- 支持断点续传：进程崩溃后重跑不会重复已完成的标注

## 为什么深层判断必须包含反证
- 没有反证的判断是确认偏误（confirmation bias）
- 五角色法庭的「辩护人」角色专门寻找善意解释和反面证据
- 每个 L1-L3 判断必须有：支持证据、反证、替代解释、置信度、判断错误代价
- 用户指令：「最激进的分析策略」意味着不放过任何可能的盲点

## 为什么用异步而非同步
- 同步 urllib：单 worker ~1.6/min，19 workers ~11/min
- 异步 aiohttp：连接复用，32 workers 预估 ~40K tok/min
- 同步模式下 worker 等待 API 响应时完全空闲
- 异步模式下 worker 可以在等待时处理其他请求

## 为什么专用 writer 线程
- SQLite 写锁是瓶颈：多个 worker 同时写入会冲突
- 专用 writer 批量提交减少锁竞争
- JSONL 分片保证崩溃时数据不丢失
- API worker 不直接争抢写锁，提高整体吞吐
