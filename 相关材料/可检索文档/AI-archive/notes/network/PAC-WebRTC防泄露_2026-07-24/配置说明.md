# PAC 分流与 WebRTC 防泄露配置记录

## 结论

用户所说的“webftc”应为 **WebRTC**。PAC（Proxy Auto-Config）不是完整 VPN：它负责为 HTTP/HTTPS 等请求选择代理，浏览器中的 `ws://`、`wss://` 通常也随 HTTP 代理规则处理，但 WebRTC 的 UDP/STUN 流量可能绕过 PAC，直接暴露真实公网 IP。

本次保留现有 v2rayN PAC 分流，在容易产生 WebRTC 的浏览器和 Chromium 桌面应用上增加两层保护：

1. Chrome、Edge 使用官方 WebRTC IP 处理策略，禁止非代理 UDP；
2. 指定应用的出站 UDP 由 Windows 防火墙阻断，TCP 保持允许。

因此，HTTP、HTTPS 和 WebSocket 的 TCP 通信不受阻断；WebRTC 只能回退到代理/TCP 路径，无法直接通过 UDP/STUN 绕过 PAC。

## 已应用的浏览器策略

### Google Chrome

- 注册表：`HKEY_LOCAL_MACHINE\SOFTWARE\Policies\Google\Chrome`
- 值名：`WebRtcIPHandling`
- 类型：`REG_SZ`
- 值：`disable_non_proxied_udp`

### Microsoft Edge

- 注册表：`HKEY_LOCAL_MACHINE\SOFTWARE\Policies\Microsoft\Edge`
- 值名：`WebRtcLocalhostIpHandling`
- 类型：`REG_SZ`
- 值：`disable_non_proxied_udp`

策略作用：WebRTC 只使用代理支持的 UDP，否则回退到 TCP，避免使用未代理的公网接口。浏览器可能显示“由贵单位管理”，这是本机策略被识别的正常提示，不代表电脑加入了企业组织。

## 已应用的防火墙规则

规则组：`AI-archive WebRTC Leak Protection`

以下 7 条规则均为：启用、出站、阻断、任意网络配置文件、仅 UDP。

## 使用影响

- HTTP、HTTPS、`ws://` 和 `wss://` 使用 TCP，不受这些 UDP 阻断规则影响。
- Chrome、Edge 的 QUIC/HTTP3 会回退至 TCP/HTTP2，首次连接可能略慢。
- WebRTC 语音、视频通常会尝试 TCP/TURN 回退，可能出现连接稍慢或质量下降。
- 如果某应用只支持直连 UDP、没有 TCP/TURN 回退，其语音或视频功能可能不可用；文字聊天和普通网页通信不受影响。
- 这些规则只保护列出的应用。其他支持 WebRTC 的新浏览器或新桌面应用，需要另外添加规则；若希望覆盖所有程序和全部 UDP，应升级代理软件后使用经过验证的 TUN 分流，而不是继续依赖 PAC。

## 关于 v2rayN 版本

当前 v2rayN 2.31 是 2019 年版本，没有现代 v2rayN 的 TUN 接管能力。此次为避免破坏现有节点、订阅和联网状态，没有升级或替换它。

若以后升级，建议单独执行一次完整迁移：先备份 `C:\Program Files (x86)\V\`，再将旧节点迁移到最新版 v2rayN，验证 PAC、DNS、订阅和 TUN 后再切换。PAC 与 TUN 不应同时作为主接管模式使用。

## 文件与回滚

- 应用脚本：`Apply-WebRTCLeakProtection.ps1`
- 回滚脚本：`Remove-WebRTCLeakProtection.ps1`

回滚时，以管理员身份运行 `Remove-WebRTCLeakProtection.ps1`。脚本只删除本次创建的 7 条固定名称防火墙规则，以及本次新增的两个浏览器策略值；不修改 v2rayN 的 PAC、节点、订阅或其他防火墙规则。
