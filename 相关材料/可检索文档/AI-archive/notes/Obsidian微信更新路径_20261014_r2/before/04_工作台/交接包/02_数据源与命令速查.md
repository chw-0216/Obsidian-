## 1.5 ★ 两个脚本的只读审计（2026-10-14 · 逐行核过）

### 参数与范围

| 脚本 | 参数 | 实际范围 |
|---|---|---|
| `index-incremental.py` | 无参数 / `--reconcile` / `--include-noise` | **没有单会话过滤**。默认遍历全部非噪音会话，水位 = **全局 `MAX(ts) - 60` 秒**；`--reconcile` 重扫全部历史；`--include-noise` 额外包含两个已排除的噪音群 |
| `gen_live_json.py` | `--who <displayName>` | 有单会话过滤，但**必须与 `_sync_state.json` 里的 name 完全一致**，**不能传 talker**；无参数则生成状态表里全部会话 |

### 依赖与读写边界

- 两者**仅用标准库 + 可选的 `zstandard`**；无下载、无网络请求、无发消息、无服务或计划任务变更。
- ★★ **缺 `zstandard` 不会报错停下，而会悄悄把压缩文本变成占位符** → 先跑一次 `python -c "import zstandard"` 确认。
- 均以 SQLite URI `mode=ro` 读源库，**代码不改原始库 / 解密库**。
- `index-incremental.py` 写 `index.sqlite`，会设 `journal_mode=WAL` → **可能同时生成 `index.sqlite-wal` / `-shm`**；**会更新不相关会话**，也可能升级既有 `[type…]` 消息的内容与发送者，**不是纯追加**。
- `gen_live_json.py` 写 `07_聊天记录分析\weflow_live\<displayName>.json`，并**重写整份 `_sync_state.json`**（即使只处理一个会话）。

### ★ 七个必须知道的缺陷

| # | 缺陷 | 后果 / 对策 |
|---|---|---|
| 1 | **JSON 生成器会删旧备份** | 消息数变化时复制 `.json.bak-时间`，随后 `prune_backups` 把超过 3 份的旧备份 `unlink()`。**只想更新后查询，不必跑它** |
| 2 | **默认索引会漏迟到消息** | 水位是**全局** `MAX(ts)-60`，不是各会话水位 → 后来补入但发送时间更早的消息会跳过。`--reconcile` 可补，但是**全会话全量**操作 |
| 3 | **不一般性纠正旧消息角色** | 同 `(session_key, server_id)` 时，仅旧内容以 `[type` 开头才升级；已有可读文本即使 `sender/role` 误标也不修 → **不能靠「跑过 reconcile」宣称发言归属已全部纠正** |
| 4 | **JSON 生成器有图片类型改写错误** | 在「自己的消息」分支把 `type==1` 改成 `0`（1=图片、0=文本）→ **自己发的图片可能被误标成文本**；重复条件 `m["type"]==1 or m["type"]==1` 也像残留 |
| 5 | **JSON 不保证字节幂等** | 每次 `syncAt` 都写当前时间；备份只比较 `totalCount` → **数量相同但内容修正时无备份**；`write_text` 直接覆盖，非原子替换 |
| 6 | **索引统计可能不等于真新增** | 按候选批次 `len(batch)` 更新 `sessions.message_count`，但消息用 `INSERT OR IGNORE` → 被忽略的候选仍可能计入。**真新增要以末尾 `after_n-before_n` 和目标会话前后计数核对** |
| 7 | **`rglob` 只取第一份** | 每种源文件仅用命中的第一份；表读取异常被直接 `continue` → **程序成功 ≠ 所有分片都读全** |

### ★ 最小维护顺序（推荐）

```
① 确认 zstandard 可导入（python -c "import zstandard"）
② 解密（chattrace data decrypt --account-dir <微信数据目录>）
③ 跑 index-incremental.py 无参数 → 核对「母亲消息条数」与「最新时间」两个数
④ 直接只读目标会话（tools\wx_read.py）
⑤ 只在发现时间较早的迟到消息时，才考虑 --reconcile
```

> ★ **不需要跑 `gen_live_json.py`** —— 它带备份删除副作用，而查询用 `index.sqlite` 就够了。

## 6. 坑表（全部实测踩过）

| 坑 | 结论 |
|---|---|
| `--account-dir` 传错 | 传 `xwechat_files\<wxid>_db45`，不是 ChatTrace accounts |
| 解密脚本报依赖缺失 | ① 步**只能用系统 Python 3.12** |
| SQL 用 `strftime` 比时间 → 0 行 | `ts` 是**整数 epoch**，要传 `int(datetime(...).timestamp())` |
| FTS 搜中文搜不到 | 分词器是 `trigram`，**需 ≥3 字**；2 字走 `LIKE` |
| 搜短数字命中上千条 | 全是 `aeskey` / base64 噪音 → **必须限定会话 + 看原文** |
| 转账笔数/金额翻倍 | 微信**每笔记两行**（`them`+`me`，逐字相同）→ 先去重 |
| 群名/会话名为空 | 查 `contact.db` 按 `username` 取 `nick_name` |
| Windows 控制台中文截断 | 长结果**写文件再读**；脚本已 `reconfigure(utf-8)` |
| 原始消息表名对不上 | 表名 = `Msg_` + `md5(talker)`；`message_content` 是 Zstd blob |
| 同 talker 表跨库 | 可能同时在 `message_0.db` 和 `message_1.db` |
| 删除文件被闸门拦 | 本机 `SAFE_DELETE_BULK_CONFIRM_REQUIRED`（50/轮）→ 走 `tools\recycle.py` |
| 生成器不幂等 | 「读旧→重写」必须断言**两次字节数一致** |
