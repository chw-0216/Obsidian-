## 1. 微信数据更新与核验（2026-10-14-r2）

适用于已授权维护现有索引、随后查询指定会话的任务。日常增量路径可以沿用；实时完整性、历史覆盖与发言归属需要分别核验。操作使用 **PowerShell + 指定 Python 3.12**。

```text
微信客户端完成所需消息同步
  → ChatTrace 解密 → decrypted 派生库
  → index-incremental.py → index.sqlite
  → 指定 talker / 时间窗口只读核验与取证
  → 获授权后写入对应 Obsidian 人工笔记并核对
```

### 范围先定清楚

| 请求 | 执行范围 |
|---|---|
| 只读查询现有记录 | 直接只读现有索引，报告数据覆盖截至时间 |
| 已授权更新既有派生库与全库索引 | 解密，再增量维护全部非噪音会话；查询正文仍限定到本次指定会话 |
| 补历史或验证完整覆盖 | 先定位缺口；`--reconcile` 是全会话历史扫描，也不能修复所有去重、角色与媒体问题 |
| 写进 Obsidian | 依本人写入授权落到指定人工笔记；索引刷新本身不会更新笔记或分析库 |

### 推荐顺序与验收

1. 确认账号、目标 `talker`、时间窗口和已授权的写入范围。维护前保存实际消息数、目标最新时间和 FTS 问题数；停用并发维护，保留可恢复快照。WAL 模式的索引使用 SQLite backup API 取得一致性备份，不能只复制主 `.sqlite` 文件，也不清理旧备份。
2. 确认指定 Python 可导入 `zstandard`、`Cryptodome`、`chattrace`；核对源账号路径、输出路径、磁盘空间和分片。当前索引器只枚举 `message_0/1.db` 与 `biz_message_0/1/2.db`；每个文件名应唯一，缺片、多份或出现新编号时先报告覆盖缺口。
3. 确认电脑微信已同步所需消息。ChatTrace 当前只读主 `.db` 文件，**不合并源 WAL**，且新鲜度只比较主库大小和修改时间。旁边有 WAL 不等于一定有漏项，但退出码 0、`fresh` 或较新的 mtime 都不能证明“同步到现在”。核不准时报告可见截至时间；可请本人正常同步并退出微信后再核，不对加密源库强行 checkpoint、删 WAL 或强杀进程。
4. 执行解密，检查退出码及 `failed` 项。解密写入 `decrypted`，逐库临时文件替换；源码在替换后才做 smoke test，失败不能保证旧好副本仍在。任何失败先停在这里，按具体文件复查，不直接继续索引。
5. 无参数运行索引器，核对 `after_n - before_n`、目标会话实际 `COUNT(*) / MAX(ts)`、FTS 缺失／孤儿／字段错配与预期源记录。记录并发情况，不能把 `sessions.message_count` 或脚本“新增”提示独立当作真新增。
6. 直接只读目标会话取证。涉及旧消息归属或关键结论时，回查解密源的实际行；`--reconcile` 不会一般性纠正已可读旧消息的角色。图片、语音、附件占位符只证明存在，原件仍需另行读取。
7. 获授权写 Obsidian 时，保留数据集／会话／消息 ID 或时间定位、事件时间、核验时间、覆盖缺口；区分原记录、本人报告、解释与完成证据。生成页沿 [[00_规范与模板/02_写入责任与路径登记|维护分工]] 的人工区／上游机制处理，完成后核对链接与变更记录。

### PowerShell 维护命令

以下命令会写派生解密库和全库索引；仅在维护范围已获授权、前述快照与源新鲜度检查完成后执行。它不调用 JSON 生成器。每步失败即停止。

```powershell
$wxPy = 'C:\Users\wardc\AppData\Local\Programs\Python\Python312\python.exe'
$wxAccount = 'C:\Users\wardc\xwechat_files\wxid_zn4ozsnn8esr21_db45'
$wxIndexScript = 'C:\Users\wardc\Desktop\_im_tmp\wechat-mcp\index-incremental.py'
$wxIndex = 'C:\Users\wardc\Desktop\_im_tmp\wechat-mcp\index.sqlite'
foreach ($wxPath in @($wxPy, $wxAccount, $wxIndexScript, $wxIndex)) {
    if (-not (Test-Path -LiteralPath $wxPath)) { throw "路径不存在：$wxPath" }
}
& $wxPy -B -c "import zstandard, Cryptodome, chattrace; print('DEPENDENCIES_OK')"
if ($LASTEXITCODE -ne 0) { throw '运行时或依赖检查失败' }

& $wxPy -B -m chattrace.cli data decrypt --account-dir $wxAccount
if ($LASTEXITCODE -ne 0) { throw '解密失败，先检查 failed 项' }

& $wxPy -B $wxIndexScript
if ($LASTEXITCODE -ne 0) { throw '索引维护失败，进入只读核查' }
# 随后执行下方只读验收，并按目标会话取证；维护命令返回 0 不代替验收。
```

`--account-dir` 必须指向微信账号目录（含 `db_storage`），不是 ChatTrace 的 `accounts` 或 `decrypted`。本轮核实 Python 3.12.10 的 `chattrace` 导入来自 `Desktop\_im_tmp\chattrace\src\chattrace`；换版本、换账号或脚本哈希变化后重新核对，不照搬旧成功记录。

### 只读验收 SQL

以 `file:...index.sqlite?mode=ro` 连接并设 `PRAGMA query_only=ON`；`:talker` 使用绑定参数，取实际稳定会话标识。维护前后分别在一致的读事务中执行，输出仅是统计值：

```sql
SELECT COUNT(*) AS actual_count, MIN(ts) AS first_ts, MAX(ts) AS last_ts
FROM messages WHERE session_key = :talker;

SELECT COUNT(*) AS fts_missing
FROM messages m LEFT JOIN messages_fts f ON f.rowid = m.id
WHERE m.session_key = :talker AND f.rowid IS NULL;

SELECT COUNT(*) AS fts_orphans
FROM messages_fts f LEFT JOIN messages m ON m.id = f.rowid
WHERE f.session_key = :talker AND m.id IS NULL;

SELECT COUNT(*) AS fts_mismatches
FROM messages m JOIN messages_fts f ON f.rowid = m.id
WHERE m.session_key = :talker AND (
    COALESCE(m.content, '') <> COALESCE(f.content, '') OR
    COALESCE(m.sender, '') <> COALESCE(f.sender, '') OR
    COALESCE(m.session_key, '') <> COALESCE(f.session_key, '')
);
```

三个 FTS 问题数为 0 只支持当前核验范围内的索引对应关系，不能证明源历史已全收齐或发言归属正确。新增为 0 也可能只是本次窗口没有新记录，不能直接当成故障。

### 兼容支路与当前工程缺口

本维护路径不依赖 WeFlow API。旧 `刷新实时数据.cmd` 会顺带运行 `gen_live_json.py`；旧 `刷新微信索引.cmd` 还会调用清表重建的 `indexer.mjs`。它们不作为本路径入口。

`gen_live_json.py` 仅在确实需要旧 JSON 消费者、且导出写入与备份清理范围已明确时单独评估；现有备份删除、类型映射和非原子覆盖问题见下节。

本轮还确认以下缺口，登记为待处理代码问题，**本轮未修复**：

- **去重可能先误删候选**：索引器先比较 `(会话, 秒级时间, 内容前80字, sender)`，再判断 `server_id`；不同 ID 的同秒同前缀消息仍可能被跳过，`--reconcile` 不能消除这个问题。`server_id` 为 0／空的情况也需专门核对。
- **分片与错误覆盖不完整**：固定文件名、`rglob` 只取第一份、表异常静默跳过；当前命令成功不等于每片和每表完整。
- **FTS 内容升级不全**：占位符升级会改消息的 `sender/role`，而对应 FTS 仅更新 `content`；验收应包含 sender 和 session 字段错配。
- **源与输出快照**：源 WAL 未合并，解密不是跨库事务快照；解密后冒烟校验不能代替所需表读取或全面完整性检查，且校验发生在替换之后。
- **下游各自有版本**：刷新索引不会自动更新 `analysis.sqlite`、旧 JSON、Obsidian 报告或纠偏层。各消费者的最近处理时间与证据修订需分别记录，不自动运行主管线重建。

主要代码定位：`chattrace\service\decryptor.py`（源发现、新鲜度、替换与 smoke test）、`chattrace\cli.py`（解密返回码）、`index-incremental.py`（固定分片、水位、去重、FTS与计数）、`gen_live_json.py`（兼容支路副作用）。本次只读检查指定源码与元数据；未读取密钥、未执行维护。后续工程优先处理 WAL／一致性、主键去重、逐会话水位、可见失败清单和一致性备份。

## 1.5 ★ 两个脚本的只读审计（2026-10-14 · 逐行核过）

### 参数与范围

| 脚本 | 参数 | 实际范围 |
|---|---|---|
| `index-incremental.py` | 无参数 / `--reconcile` / `--include-noise` | **没有单会话过滤**。默认遍历全部非噪音会话，水位 = **全局 `MAX(ts) - 60` 秒**；`--reconcile` 重扫全部历史；`--include-noise` 额外包含两个已排除的噪音群 |
| `gen_live_json.py` | `--who <displayName>` | 有单会话过滤，但**必须与 `_sync_state.json` 里的 name 完全一致**，**不能传 talker**；无参数则生成状态表里全部会话 |

### 依赖与读写边界

- 两者**仅用标准库 + 可选的 `zstandard`**；无下载、无网络请求、无发消息、无服务或计划任务变更。
- ★★ **缺 `zstandard` 不会报错停下，而会悄悄把压缩文本变成占位符** → 先跑一次 `python -c "import zstandard"` 确认。
- 本节的索引器和 JSON 生成器均以 SQLite URI `mode=ro` 读解密库。**ChatTrace 解密阶段另会写入／替换派生解密库**，见上节；整条更新路径不能称为全程只读。
- `index-incremental.py` 写 `index.sqlite`，会设 `journal_mode=WAL` → **可能同时生成 `index.sqlite-wal` / `-shm`**；**会更新不相关会话**，也可能升级既有 `[type…]` 消息的内容与发送者，**不是纯追加**。
- `gen_live_json.py` 写 `07_聊天记录分析\weflow_live\<displayName>.json`，并**重写整份 `_sync_state.json`**（即使只处理一个会话）。

### ★ 七个必须知道的缺陷

| # | 缺陷 | 后果 / 对策 |
|---|---|---|
| 1 | **JSON 生成器会删旧备份** | 消息数变化时复制 `.json.bak-时间`，随后 `prune_backups` 把超过 3 份的旧备份 `unlink()`。**只想更新后查询，不必跑它** |
| 2 | **默认索引会漏迟到消息** | 水位是**全局** `MAX(ts)-60`，不是各会话水位 → 后来补入但发送时间更早的消息会跳过。`--reconcile` 可补，但是**全会话全量**操作 |
| 3 | **不一般性纠正旧消息角色** | 同 `(session_key, server_id)` 时，仅旧内容以 `[type` 开头才升级；已有可读文本即使 `sender/role` 误标也不修 → **不能靠「跑过 reconcile」宣称发言归属已全部纠正** |
| 4 | **JSON 生成器有图片类型改写错误** | 在「自己的消息」分支把 `type==1` 改成 `0`（1=图片、0=文本）→ **自己发的图片可能被误标成文本**；重复条件 `m["type"]==1 or m["type"]==1` 也像残留 |
| 5 | **JSON 不保证字节幂等** | 每次 `syncAt` 都写当前时间；备份只比较 `totalCount` → **数量相同但内容修正时无备份**；`write_text` 直接覆盖，非原子替换 |
| 6 | **索引统计可能不等于真新增** | 按候选批次 `len(batch)` 更新 `sessions.message_count`，但消息用 `INSERT OR IGNORE` → 被忽略的候选仍可能计入。**真新增要以末尾 `after_n-before_n` 和目标会话前后计数核对** |
| 7 | **`rglob` 只取第一份** | 每种源文件仅用命中的第一份；表读取异常被直接 `continue` → **程序成功 ≠ 所有分片都读全** |

### 审计后的执行指引

统一按本页第 1 节 **2026-10-14-r2** 执行，包含写入边界、WAL／分片检查、快照、停止条件、统计与 FTS 验收及授权后的 Obsidian 回写。只查询索引时跳过 JSON；迟到消息需先定位，再评估全量 `--reconcile`。

## 6. 坑表（全部实测踩过）

| 坑 | 结论 |
|---|---|
| `--account-dir` 传错 | 传 `xwechat_files\<wxid>_db45`，不是 ChatTrace accounts |
| 解密脚本报依赖缺失 | ① 步**只能用系统 Python 3.12** |
| SQL 用 `strftime` 比时间 → 0 行 | `ts` 是**整数 epoch**，要传 `int(datetime(...).timestamp())` |
| FTS 搜中文搜不到 | 分词器是 `trigram`，**需 ≥3 字**；2 字走 `LIKE` |
| 搜短数字命中上千条 | 全是 `aeskey` / base64 噪音 → **必须限定会话 + 看原文** |
| 转账笔数/金额翻倍 | 微信**每笔记两行**（`them`+`me`，逐字相同）→ 先去重 |
| 群名/会话名为空 | 查 `contact.db` 按 `username` 取 `nick_name` |
| Windows 控制台中文截断 | 长结果**写文件再读**；脚本已 `reconfigure(utf-8)` |
| 原始消息表名对不上 | 表名 = `Msg_` + `md5(talker)`；`message_content` 是 Zstd blob |
| 同 talker 表跨库 | 可能同时在 `message_0.db` 和 `message_1.db` |
| 删除文件被闸门拦 | 本机 `SAFE_DELETE_BULK_CONFIRM_REQUIRED`（50/轮）→ 走 `tools\recycle.py` |
| 生成器不幂等 | 「读旧→重写」必须断言**两次字节数一致** |
