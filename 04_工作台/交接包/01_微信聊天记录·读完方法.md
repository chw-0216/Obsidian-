## 2. 每层怎么做（命令可直接复制）

### L0 · 清点层 —— 保证「没有一个会话被漏掉」

```bash
cd "C:\Users\wardc\WorkBuddy AI\2026-09-28-06-58-18"
set PY=C:\Users\wardc\.workbuddy-ai\binaries\python\versions\3.13.12\python.exe

%PY% tools\wx_read.py sessions --top 50
```

输出：会话总数、消息总数、时间范围、按条数排序的会话表。

**覆盖率自查**（有没有会话从来没被分析过）：

```python
import sqlite3
c = sqlite3.connect('file:C:/Users/wardc/Desktop/_im_tmp/wechat-mcp/index.sqlite?mode=ro', uri=True)
# 条数 >=100 但 display_name 为空的会话 = 还没认领的
for r in c.execute("""select talker, message_count from sessions
                      where (display_name is null or display_name='') and message_count>=100
                      order by message_count desc limit 30"""):
    print(r)
```

> 会话名为空 → 去解密库 `contact.db` 按 `username='xxx@chatroom'` 取 `nick_name`。

### L1 · 会话层 —— 每人一张卡

```bash
%PY% tools\wx_read.py card 刘丽萍        # 用显示名
%PY% tools\wx_read.py card deerluna      # 用 talker（更准）
```

一张卡包含：条数 / 时间跨度 / **双方角色占比** / 消息类型占比 / **按月分布柱图**。

**怎么读这张卡**：
- 双方占比 ≈ 50/50 → 对话型关系
- 一方 > 70% → **单方输出**，要警惕「我以为在聊，其实是我在发」
- 按月分布出现断崖 → 找断点那天发生了什么（下钻 L2）

> ★ 已知陷阱：**显示名 ≠ 真名**。陈晔的私聊显示名是「**导！急速回，三思回得体！**」，
> 用 `card 陈晔` 会误命中一个同名群。**查人优先用 `session_map.md` 里的 talker。**

### L2 · 事件层 —— 关键词 + 时间锚点

```bash
%PY% tools\wx_read.py search 版画工作坊 --top 30
%PY% tools\wx_read.py search 3500 --session 刘丽萍        # 限定单会话
%PY% tools\wx_read.py search 版画工作坊 --raw             # 不过滤媒体噪音
%PY% tools\wx_read.py timeline 转账 --top 200
```

- **≥3 字** → 走 FTS5 trigram（快、支持模糊）
- **<3 字** → 自动降级 `LIKE`
- **默认过滤媒体噪音**（`<img`/`<videomsg`/`aeskey` 等）

> ★★ **最重要的一条口径**：短数字/短词在微信里**几乎全是 base64 噪音**。
> 实测：全库搜 `3500` 命中 **1,476 条**，其中绝大部分是 `aeskey=` / 图片占位。
> **数字类检索必须限定会话，且必须看原文上下文**，否则结论会完全错。

### L3 · 证据层 —— 回到原话

```bash
%PY% tools\wx_read.py tail deerluna --n 30      # 看某会话最新 30 条
```

任何结论落不进原文 → 标成「假设」，**不许当结论用**。

### L4 · 裁定层 —— 定稿

写进引擎 `05-纠偏层.md`，**编号递增**，同时同步「打通页 + 受影响笔记」。
编号越大越新。**读的时候只读编号最大的那几节，前面的是历史。**

## 3. 七个口径（错了结论必歪）

| # | 口径 | 后果 |
|---|---|---|
| 1 | **只读**（`file:...?mode=ro`） | 永不写入微信数据 |
| 2 | **时间窗起 2024-11-10** | 早于此**不得读成「没关系」**，只能说「数据未覆盖」 |
| 3 | **转账每笔记两行**（`them`+`me`，内容逐字相同） | 不去重 → 笔数/金额**翻倍** |
| 4 | **短数字/短词 = 噪音重灾区** | 必须限定会话 + 看原文 |
| 5 | **FTS trigram 需 ≥3 字** | 2 字人名用 `LIKE` |
| 6 | **`ts` 是整数 epoch** | SQL 里 `ts > strftime(...)` **不生效**，要传整数 |
| 7 | **「零消息」≠「没聊过」** | 标签不全**只作线索**，不作结论 |

## 4. 增量维护（每天 / 每周）

**每次新聊天要进库，跑三步**（详见 `02_数据源与命令速查.md` §1.5）：

```bash
# ⓪ 先确认 zstandard 可导入 —— 缺它不会报错，会静默把压缩文本变成占位符
python -c "import zstandard"

# ① 解密（★ 只能用系统 Python 3.12；--account-dir 传微信自己的数据目录）
chattrace data decrypt --account-dir "C:\Users\wardc\xwechat_files\wxid_zn4ozsnn8esr21_db45"

# ② 增量并入索引
%PY% "C:\Users\wardc\Desktop\_im_tmp\wechat-mcp\index-incremental.py"
```

★ **第③步 `gen_live_json.py` 通常不需要跑** —— 它有**备份删除副作用**（保留 3 份后 unlink 旧备份），
而查询用 `index.sqlite` 就够了。**只想「更新后查询」，做完 ① ② 即可。**

- **每周**：`index-incremental.py --reconcile`（对账）+ 查 FTS 孤儿
- 判据：`messages` 条数应 1:1 等于 `messages_fts` 条数
- ★ **每次跑完必须核对**「消息总数」和「最新时间」两个数

> ⚠️ **两个已知缺陷（2026-10-14 审计）**：
> ① 默认水位是**全局** `MAX(ts)-60`，不是各会话水位 → **后来补入但发送时间更早的迟到消息会被跳过**（要 `--reconcile` 才补）。
> ② 跑过 `--reconcile` **不等于**「发言归属已全部纠正」—— 脚本不一般性修正旧消息的 `sender/role`。
